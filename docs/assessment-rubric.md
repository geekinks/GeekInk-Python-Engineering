# Assessment Rubric

**GeekInk Python Engineering — 100 Days. 100 Challenges. Real Engineering.**

This rubric defines the evaluation framework for all student work in the GeekInk Python Engineering program, including daily challenges, module milestone projects, and the final capstone.

## Grading Framework Overview

| Category | Weight |
| :--- | :---: |
| Conceptual Understanding | 20% |
| Practical Implementation | 30% |
| Code Quality and Engineering Practices | 20% |
| Project Completion | 20% |
| Documentation and Presentation | 10% |

Each category is scored on a four-level scale: **Excellent**, **Good**, **Satisfactory**, and **Needs Improvement**.

---

## Category 1: Conceptual Understanding (20%)

Evaluates whether the student understands the underlying concepts, not just the syntax.

| Level | Score Range | Criteria |
| :--- | :---: | :--- |
| Excellent | 90-100% | Demonstrates deep understanding. Can explain concepts in their own words, identify edge cases, and relate topics to broader engineering principles. Reflection answers show original thinking. |
| Good | 70-89% | Demonstrates solid understanding. Explains concepts accurately with minor gaps. Reflection answers address the core ideas. |
| Satisfactory | 50-69% | Demonstrates basic understanding. Can follow examples but struggles to explain concepts independently. Reflection answers are shallow or incomplete. |
| Needs Improvement | 0-49% | Does not demonstrate understanding. Submissions suggest code was copied without comprehension. Reflections are missing or unrelated to the topic. |

### Evidence Sources

- Reflection responses in daily submissions.
- Explanation comments in code.
- Answers to knowledge-check questions.
- Verbal explanations during reviews or presentations.

---

## Category 2: Practical Implementation (30%)

Evaluates the correctness, completeness, and functionality of submitted code.

| Level | Score Range | Criteria |
| :--- | :---: | :--- |
| Excellent | 90-100% | All daily challenges and exercises are complete and correct. Solutions handle edge cases. Code runs without errors. Tests pass where provided. |
| Good | 70-89% | Most challenges are complete and correct. Minor bugs or missing edge cases. Code runs with minimal issues. |
| Satisfactory | 50-69% | Some challenges are complete. Solutions work for basic cases but fail on edge cases or have significant bugs. |
| Needs Improvement | 0-49% | Few challenges attempted. Submissions contain syntax errors, do not run, or produce incorrect results. |

### Evidence Sources

- Daily challenge solutions.
- Guided practice submissions.
- Module milestone project functionality.
- Test results (where applicable).

---

## Category 3: Code Quality and Engineering Practices (20%)

Evaluates how professionally the code is written, organized, and managed.

| Level | Score Range | Criteria |
| :--- | :---: | :--- |
| Excellent | 90-100% | Code is clean, well-structured, and follows PEP 8. Functions are focused and reusable. Variables have meaningful names. Git commits are atomic and descriptive. Error handling is appropriate. |
| Good | 70-89% | Code is generally clean with minor style issues. Functions are used appropriately. Git history shows regular commits with reasonable messages. |
| Satisfactory | 50-69% | Code works but is poorly organized. Long functions, unclear variable names, or inconsistent style. Git commits are infrequent or have vague messages like "update" or "fix." |
| Needs Improvement | 0-49% | Code is disorganized, difficult to read, or all in one block. No use of functions. No meaningful Git history. Secrets or generated files included in submissions. |

### Evidence Sources

- Code structure and style in submissions.
- Git commit history and messages.
- Pull request quality.
- Use of `.gitignore` and proper file organization.

---

## Category 4: Project Completion (20%)

Evaluates delivery of module milestone projects and the final capstone.

| Level | Score Range | Criteria |
| :--- | :---: | :--- |
| Excellent | 90-100% | All milestone projects delivered on time with all required features. Capstone project demonstrates original thinking, complete implementation, and thorough testing. |
| Good | 70-89% | Most milestone projects delivered. Capstone project is functional with most required features. Minor gaps in scope or testing. |
| Satisfactory | 50-69% | Some milestone projects delivered. Capstone project is partially functional or missing significant features. |
| Needs Improvement | 0-49% | Few or no milestone projects delivered. Capstone project is absent, non-functional, or does not meet minimum requirements. |

### Evidence Sources

- Milestone project submissions for each module.
- Capstone project deliverables.
- Feature completeness against project requirements.

---

## Category 5: Documentation and Presentation (10%)

Evaluates the quality of written documentation and verbal or visual presentation.

| Level | Score Range | Criteria |
| :--- | :---: | :--- |
| Excellent | 90-100% | Project README files are comprehensive, clear, and well-formatted. The student can present their work confidently, explain design decisions, and answer questions. |
| Good | 70-89% | README files cover the essentials. Presentation is clear with minor gaps in explanation. |
| Satisfactory | 50-69% | README files exist but are incomplete or poorly formatted. Presentation is disorganized or lacks depth. |
| Needs Improvement | 0-49% | No README files or documentation. Unable to present or explain their work. |

### Evidence Sources

- Project README files.
- Pull request descriptions.
- Capstone presentation and defense.

## Module Milestone Evaluation

Each module (10 days) culminates in a milestone project. Milestones are evaluated on:

| Criterion | Description |
| :--- | :--- |
| Requirements Coverage | Does the project address the stated problem and implement the required features? |
| Technical Depth | Does the project apply the concepts learned in the module? |
| Code Organization | Is the project structured with clear separation of concerns? |
| Error Handling | Does the project handle invalid input and edge cases gracefully? |
| Testing | Are there tests, and do they pass? |
| Documentation | Does the project include a README explaining the problem, how to run it, and its design? |

Milestones contribute to the **Project Completion** and **Practical Implementation** categories.

---

## Capstone Project Evaluation

The capstone (Module 10, Days 91-100) is the culminating assessment. It is evaluated more rigorously:

| Criterion | Weight | Description |
| :--- | :---: | :--- |
| Problem Definition | 10% | Is the problem clearly stated, scoped, and relevant? |
| Architecture and Design | 15% | Is the solution well-designed with appropriate abstractions, data models, and component separation? |
| Implementation | 25% | Is the solution correctly implemented, functional, and complete? |
| Testing | 15% | Are there meaningful tests with good coverage? |
| Code Quality | 15% | Does the code follow professional standards (PEP 8, clean structure, meaningful names)? |
| Documentation | 10% | Is there a comprehensive README, setup instructions, and usage guide? |
| Presentation and Defense | 10% | Can the student present, explain design decisions, and answer technical questions? |

See the [Capstone Guidelines](capstone-guidelines.md) for full requirements.

---

## Grade Scale

| Grade | Percentage | Description |
| :--- | :---: | :--- |
| Distinction | 90-100% | Exceptional performance across all categories |
| Merit | 70-89% | Strong performance with consistent quality |
| Pass | 50-69% | Meets minimum requirements with room for improvement |
| Incomplete | 0-49% | Does not meet minimum requirements; further work needed |

Students scoring below 50% in any individual category will receive targeted feedback and an opportunity to resubmit within a timeframe set by the instructor.
